# picacg 2.6.73：登录与协议分析（已用 REA 复核）

## 结论与范围

**已实际使用 REA 6.8.0 + JADX headless 0.7.1 + 完整 JDK21.0.13，复核原始 DEX 分析。** 登录、HMAC 签名、nonce 和 Token 保存的核心结论一致，并补齐 HTTP 调度/TLS、app-uuid、QueryMap、JSON 配置及模型字段证据。

- 项目内隔离部署；没有修改系统 PATH、DSH MCP 配置、REA 源码或 APK。
- 保存 **1,056 个成功 REA 操作结果**，其中 808 次方法读取（618 Java、190 smali；含重复读取），并保留完整 Evidence 的 APK/JAR/bridge 哈希。不是“1,056 个协议”，也不代表逐条证明所有反编译控制流正确。
- PICA 接口 **33/33 完整方法签名** 与 REA 成员清单一致；原 APK 的 8 类 Retrofit HTTP 注解共匹配 **42 个方法**。
- 已识别的 **62 个序列化模型、299 个字段注册**，wire key / optional 均与原 DEX 对照一致。懒加载/泛型子类型保留原表达式，不编造服务端 schema。
- **未启动 APK、未登录账户、未发送目标业务请求。** 以下是静态客户端实现，不是在线抓包、服务器验签或真实登录成功证明。工具安装曾联网下载公开依赖。

## 2. 登录流程

已复核的静态调用关系（不是运行时堆栈；R8 合并类有其他业务分支）：

```text
登录 UI eo3.c
  → username.replace("@", "")；password 原样传递
  → hi6.c → bb3.invokeSuspend
  → dg4.a：await readiness、HTTP 错误包装、业务响应校验/解包
  → l31.invokeSuspend：new SignInRequest(email,password)
  → eg4.h：POST auth/sign-in
  → LoginData.token → nh4.f：内存缓存 + 本地加密保存
  → 成功 UI；按“记住密码”选择加密保存或删除已存凭据
```

- UI 分支删除**全部 `@`**，不是仅删除开头一个；未见 trim/完整邮箱标准化。DTO 的 email 命名不能证明实际发送完整邮箱地址。
- 审查的调用/DTO/writer 链未做 password hash 或应用层加密，作为 JSON String 交给 HTTPS。AES-GCM 用于**本地存储**，不是登录请求体加密；数据类 hashCode 也不是密码 hash。
- `v55.a` 是等待初始化 readiness，不是网络连通性探测。

证据：[REA UI smali](<rea/core/login-ui.smali#L195-L239>)、[登录成功链](<rea/core/login-service.java#L59-L88>)、[请求构造](<rea/core/signin-call.java#L76-L92>)、[readiness](<rea/core/preflight.java>)、[模型复核](<REA请求模型复核.md#2-六个请求根>)。

### 2.1 请求与返回契约

Retrofit base URL 绑定为 `https://picaapi.picacomic.com/`；最终 authority 会按 RequestMode 重写，见第 5 节。[REA 注入链](<rea/validation/000-priority-wj1-get.java#L151-L162>)。

```http
POST /auth/sign-in
Content-Type: application/json; charset=UTF-8
```

```json
{"email":"处理后的用户名","password":"输入密码"}
```

email/password 均 required、非 null String；这是结构示意，不是实际账户或抓包。`PicaResponse<LoginData>` 的客户端模型是：

| 键 | 类型/缺省约束 |
|---|---|
| code | Int，required |
| message | String，required |
| error | String?，optional，缺键默认 null |
| data | LoginData?，optional，缺键默认 null |
| data.token | String，required；不等于非空字符串校验 |

业务校验先判断 `error == "1023"` 并抛时间错误；其后 **message == "success" 或 code == 200** 即通过，否则抛业务错误。登录通用解包还要求 data 非 null，否则“响应 data 为 null”。这是客户端判断，不是服务器实测成功值。[业务校验](<rea/supplement/202-supp-dg4-c.java#L1-L9>)、[解包](<rea/core/api-wrapper.smali>)、[返回模型](<REA请求模型复核.md#3-logindata-与-picaresponse>)。

## 3. 请求签名与 headers

签名方法 `Lfg4;->a(Lhe3;)Ls65;`，classes3.dex，method_idx 5283，code_off `0x111120`。

```text
t = int32(System.currentTimeMillis() / 1000)
p = encodedPath，移除一个开头的 "/"
若 encodedQuery 非 null 且非空：p += "?" + encodedQuery
input = lowerCase(Locale.ROOT, p + decimal(t) + nonce + method + apiKey)
signature = lowercase_hex(HMAC_SHA256(UTF8(secret), UTF8(input)))
```

- **path → time → nonce → method → api-key**，不是 nonce → time。
- API key 为 `C69BAF41DA5ABD1FFEDC6D2FEA56B`；secret 是 APK 硬编码字符串，唯一原文定位见[REA signer:33](<rea/core/signer.java#L33>)。离线脚本从原取证 JSON 读取，避免手抄反斜杠错误。
- query 保留原 encoded 顺序/编码，不排序，随后整个拼接结果转小写。只签 path/query，不含 hostname、body 或 authorization；不是 JSON 摘要/JWT。
- HMAC 输出按原字节顺序 `%02x` 连接，为 64 位小写 hex。request.g 的 method 来源及 selector28 的 hex 分支已用原 DEX 闭环。
- signed32 秒存在 2038 静态溢出后果，但未观察服务故障。

[REA signer](<rea/core/signer.java#L4-L40>)、[原始 helper/hex/method 证据](<signature_helper_evidence.md>)、[路径/UTF-8 原始证据](<focused_dex.md>)。Bytecode PC 为 16-bit code-unit，code_off 是所属 DEX 字节偏移；自写取证脚本不是 JADX。

| Header | 客户端值 |
|---|---|
| accept | `application/vnd.picacomic.com.v1+json` |
| time / nonce / signature | 上述时间、持久 nonce、HMAC |
| api-key | `C69BAF41DA5ABD1FFEDC6D2FEA56B` |
| app-channel | `1` |
| app-version | `2.3.1.20241111` |
| app-build-version | `20250144` |
| app-platform | `android` |
| app-uuid | 第 4 节的持久化设备标识 |
| User-Agent | 显式 `okhttp/3.8.1`，不能据此断言真实库版本 |
| image-quality | 用户配置 `dd1.b` |
| authorization | Token **非 null** 时直接写入，不加 `Bearer `；空字符串未被该条件排除 |

[REA 头部/401](<rea/core/signer.java#L49-L74>)。accept 用移除同名旧头再添加的 q()；其余用 a() 路径，不能把所有 header 当成统一 replace。[q](<rea/supplement/059-supp-k30-q.java>)、[删除同名头](<rea/supplement/095-supp-ys2-q.java>)、[a](<rea/supplement/079-supp-ys2-a.java>)。

APK version 与 HTTP app-version/build-version **不同**，不能凭 APK 文件名替换请求常量。库 Bridge 的缺省 UA 字面量是 `okhttp/5.3.2`，仅缺头时补；不应覆盖 fg4 的显式 UA，也不作依赖版本证明。[UA 区分](<REA网络复核.md#52-重要纠正381-是显式-ua532-是库-bridge-的缺省-ua>)。

## 4. nonce、UUID 与 Token 生命周期

### nonce

`pica_nonce_prefs/pica_nonce` 非 null 即原样复用，含空字符串，无格式校验；缺失时构造 32 个 `0–9/a–z` 字符、保存并缓存。**不是每请求刷新，不是 UUID。** 注销/本拦截器的 401 不删除 nonce；随机 helper 使用集合随机选择，未证明为密码学 SecureRandom。[REA nonce](<rea/core/nonce.java>)、[随机选择 helper](<rea/closure/001-closure-nr0-J0.java>)。

### app-uuid

持久 `device_uuid` 合法 **32 位 hex（包括大写 A–F）**时直接复用；无效/缺失时，Android ID 非空且不是 `9774d56d682e549c` 则取其 MD5 hex，否则/异常 fallback 为去连字符的随机 UUID，再 DataStore 保存。

JADX 对 at1.c 的 Java 循环/分支损坏，不能据此报告 APK 死循环；已用原始 DEX 闭环。[UUID 原始分支复核](<REA网络复核.md#62-at1c-原始-dex-分支纠正损坏-java>)、[修正用原字节码](<rea_original_corrections.json>)。未测具体设备实际值。

### Token / 记住密码

- prefs `secure_tokens`，键 auth_token；AndroidKeyStore alias `picacg_token_key`，AES-256/GCM/NoPadding。
- 存储为 `Base64(NO_WRAP, IV || ciphertext+GCM-tag)`；解密取前 12 字节 IV，tag 128 bit，UTF-8。
- saved_username/saved_password 同 helper 加密，记住密码成功写入另有条件。
- 加密结果非 null 才持久写 auth_token，但原 Token 总被内存缓存；**加密失败不删除旧 ciphertext**，不能说磁盘必定已清空。未见明文 fallback。
- 注销/HTTP 401 删除 auth_token 与 refresh_token 并清缓存；401 的 signer 内不刷新/重试，不清 nonce。
- LoginData 只有 token；refresh_token 清理字符串不能证明完整 refresh API。未观察此 APK 声明对应刷新 endpoint，不保证没有其他运行时机制。

[Token 保存](<rea/core/token-save.java#L21-L39>)、[加密](<rea/core/token-encrypt.java>)、[解密](<rea/core/token-decrypt.java>)、[KeyStore 原始证据](<focused_dex.md#L485-L733>)、[401](<rea/core/signer.java#L69-L74>)。复杂 token-load 的 Java 丢失一个赋值，见第 7 节。

## 5. HTTP 调度、线路与 TLS

- PICA `n54` selector0 应用拦截器：`wi0(3) → wi0(2) → fg4`；网络拦截器：`ue0(...,2) → qy2`；共享缓存接入、三个秒制 timeout setter 均为 30。图片分支不挂 fg4，不能混用行为。
- `j12` 取当前 RequestMode，在客户端缓存中按模式复用客户端；只重写 URL scheme/host/port，保留 path/query。
- 四模式：official_direct（默认，SystemDns）、official_enhanced（FixedIps）、proxy1_direct（SystemDns）、smart_pool（MeasuredPool）。固定/池 IP 解析保留 hostname，不等于把 URL 改 IP 或绕过 TLS。
- v55 先默认模式，异步从 DataStore 更新，再完成 readiness。登录通用 wrapper await 该 readiness；不等于外网探测或所有入口均等待。
- 审查的 PICA 构造路径用系统 X509/CA 与 SAN hostname verifier；默认 pin 集合为空，**无 pin 不等于 trust-all**。
- 外层有边缘错误处理/GET-HEAD 重试预算，不能把“signer 内不 retry”泛化为所有网络层从不 retry；复杂 Java 尾部控制流保留不确定性。

[网络详细复核/来源](<REA网络复核.md>)。未实测线路、DNS、证书或连接；缓存目录/容量、代理 RouteTarget 域名映射、损坏旧模式的 fallback 和全部测速算法仍属有界未闭合项。

## 6. 协议与模型清单

[协议清单](<protocol_catalog.md>)逐项列 HTTP/path、Path/Query/QueryMap/Body/Tag、具体 PicaResponse.data 根类型并链接 Evidence。

PICA 33 个方法覆盖登录/注册、用户 profile/avatar/favourites/punch-in、漫画分类/搜索/章节/pages/评论/like、评论回复/report、游戏与公告/banners/collections/keywords。另有 MacCMS 5、AIBIKA 1、推荐/track 2、DNS 1，共42。**HTTP 注解全量不保证 raw socket/WebView/动态生成协议已穷尽。** 非 PICA 签名/完整返回模型未全面细审。

### QueryMap 与搜索

`GET comics`：category→c、tag→t、author→a、creatorId→ca、chineseTeam→ct（非 null 才加），sort→s 总加；customParams 最后覆盖，调用方再写 page。排序值 dd/da/ld/vd。keyword 或 categories 非 null 时走 `POST comics/advanced-search`，keyword 缺失 fallback 空串，分页仍为 query；不发明其他 query keys。

[QueryMap 说明及原始修正](<protocol_catalog.md#querymap--搜索分支>)。JADX Java 丢失前五个 put，不能照抄。

### JSON / wire schema

- [六请求根精确 key/default/null/writer](<REA请求模型复核.md>)：SignIn email/password；Register 11 个 required String；AdvancedSearch keyword required、sort 缺键 dd、categories 缺键 null；Content/avatar/slogan required String。
- [62 个模型/299 字段](<REA模型清单.md>)及[JSON 清单](<rea_model_schema.json>)：所有已识别具体根/嵌套模型的 key/optional 对照原 DEX；nullable 不等于 optional。Map Body 的具体业务键、部分 lazy/generic child 未逐个闭合，不猜。
- `JsonElement` 是任意 JSON 树，**不是 Unit 或固定空对象**。
- PICA JSON 配置已闭合：**encodeDefaults=true、ignoreUnknownKeys=true、isLenient=true、explicitNulls=true**。AdvancedSearch.sort=dd 仍写出，categories=null 却因 writer 特判省略；不能只凭全局配置推断所有字段。[配置/helper 闭环](<REA请求模型复核.md#4-json-encoder-配置与-helper-闭环>)。

## 7. 纠正与仍未证明的事项

### 本轮纠正

1. 之前“未部署/未运行 REA”状态已更新；现在有真实 REA Evidence，不是仅字符串扫描。
2. 42 的口径从 GET/POST/PUT 筛选改为穷举 parser 的 8 类 HTTP 注解；PICA 33 签名完整对照。
3. UUID、readiness、authority/DNS/TLS、JSON 配置与 wire key 已补齐；nonce 与 UUID 明确分开。
4. REA/JADX `source_status=complete` 只表示文本未截断，**不证明语义正确**：at1.c 循环、ComicListParams 前五个 put、nh4.d 公共赋值、dg4.d 某些错误分支存在反编译损坏。用[原始修正证据](<rea_original_corrections.json>)及原 DEX/smali，不将损坏 Java 报成 APK bug。
5. `eg4.h` 的 Continuation 原型是 `Lne1;`；`Lpe1;` 是不同类型，不做全局别名替换。后续批次 791 次精确 prototype 请求（787 个不同 ID）均匹配，无模糊 fallback；核心另有17次按成员重载选择。审计见[汇总](<rea_audit.json>)。

### 有界静态未决

代理具体域名/缓存 lazy 参数/saved-mode 损坏 fallback/全部测速与重试循环、Map Body 业务键及未解开的 lazy 子模型；非 PICA 完整服务协议和运行时生成请求未穷举。保留这些边界，不把“已分析此项目”写成“所有协议全解”。

### 动态未决

当前后端是否在线、签名是否被现行服务器接受、真实账号登录/验证码/风控、错误响应、Token 过期/刷新、线路/IP/证书实际可用性。静态分析不能替代这些；若进入动态阶段，需另行确定本人授权账户/设备和范围。本次未绕过认证或发送认证/注册/业务请求。
